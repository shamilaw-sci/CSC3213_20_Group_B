# Departmental staging acceptance

Use this with [Departmental deployment](DEPARTMENTAL_DEPLOYMENT.md). Record the
staging domain, deployed monorepo commit, public-data commit, image digests,
Compose project, date, and operator in the department's protected change record.
Keep credentials, cookies, OTPs, private images, and full request bodies out of
that record. **Pending** means no staging result has been observed; a local
test or a healthy container does not change it to pass. Mark each row **Pass**
or **Fail** only after its procedure and evidence are reviewed. Any failed or
pending critical row blocks production sign-off. Production approval is a
separate decision by the department after staging passes and a cutover plan is
reviewed.

Use isolated staging accounts, OAuth and GitHub App installations, SMTP relay,
TypeSafe key, PostgreSQL volume, and private S3 bucket. Do not point destructive
tests or migration commands at production. In the procedures, `dc` is the
Compose wrapper defined in [Departmental deployment](DEPARTMENTAL_DEPLOYMENT.md)
and `<domain>` is the staging base domain. Save redacted output and timestamps.

The department must supply the staging host and DNS/TLS authority, isolated
OAuth/GitHub App accounts, test users and mailboxes, SMTP and TypeSafe test
credentials, disposable PostgreSQL/S3 resources, a validated public-data
snapshot, encrypted off-host backup storage, and named operators with recovery
targets. A separate authorized cutover review must cover D1/R2 export/import,
production DNS, secrets, and reconciliation of writes after rollback. None of
those production actions is performed by this checklist.
